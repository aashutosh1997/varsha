# Varsha — iOS Workout App

A SwiftUI iOS app that runs structured workout sessions with timed/rep-based sets, automatic progression, screen-always-on, and embedded form-demonstration media (MP4 video, animated GIF, or two-frame fallback).

Ships with two plans, switchable from the person icon in the week view (the selection persists across launches):

| Plan | Structure | Focus |
|---|---|---|
| **Varsha** | 5 days (Sun–Thu) | PCOS-tailored strength + conditioning |
| **Aashutosh** | 4 days, Upper/Lower split | Hypertrophy lean-bulk + intervals |

## Tech Stack

| Layer | Choice | Why |
|---|---|---|
| Language | Swift 5.9+ | Modern concurrency, observation |
| UI | SwiftUI (iOS 17+) | Reactive UI, less boilerplate |
| State | `ObservableObject` + `@Published` | Battle-tested, Combine integration |
| Plan data | Bundled JSON + `PlanLoader` | Edit workouts without recompiling |
| Tests | Swift Testing (`@Test`, `#expect`) | Pins plan expansion output |
| Persistence (later) | SwiftData | Native Codable, less ceremony than CoreData |
| Video | `AVKit` / `AVPlayer` | Native, low overhead |
| Audio cues | `AudioServicesPlaySystemSound` + `UINotificationFeedbackGenerator` | No extra deps |
| Health (later) | HealthKit | Log workouts, calories |

## Workout Plans Are Data, Not Code

Plans live in `Resources/Plans/` as compact, hand-editable JSON. `PlanLoader` decodes them at launch and expands each block into the full set sequence — set labels, superset interleaving, and rest conventions are generated, not hand-written.

A block declares common fields (`label`, `kind`, `tag`, optional `notes`) plus **exactly one** content form:

| Form | Use for | Example |
|---|---|---|
| `straight` | N sets of one exercise | `{ "exercise": "bench-press", "sets": 4, "reps": 6, "weightKg": 40, "rest": 120 }` |
| `superset` | Interleaved pairs (A1/A2) | `{ "exercises": ["back-squat", "rdl"], "rounds": 4, "reps": 8, "rest": 90 }` |
| `rounds` | Circuits and intervals | `{ "count": 3, "items": [{ "exercise": "dead-bug", "reps": 12, "rest": 0 }, ...] }` |
| `groups` | Hand-built finishers | `[{ "exercise": "plank", "sets": 3, "durationSeconds": 45, "rest": 30 }, ...]` |
| `sets` | Raw escape hatch | One JSON object per set, expanded 1:1 |

Expansion conventions (reproduced from the original hand-written data):

- `straight` labels sets "Set i of N" and always rests **90s after the final set** before the next block, whatever the base rest.
- `superset` runs A, B, A, B… with 30s between the paired exercises and the full rest after each round, labeled "Round i of N".
- `rounds` items take an optional `restFinalRound` to change rest on the last lap only (drop to 0, or bump up before the next block); `labelStyle: "set"` switches the label wording.
- `groups` entries take `lastRest` and `labelOverride` for finisher-style irregularities.

Per-set details like `perSide`, `weightKg`, and `notes` are available on the relevant forms. Exercise ids must exist in `exercises.json` — the loader throws a descriptive error at launch (and the tests fail) if a plan references an unknown id.

### Adding a new plan

1. Create `Resources/Plans/<id>.json` (copy `aashutosh.json` as a template).
2. Add any new exercises to `exercises.json` (and to the fetcher's name-candidate maps if you want media — see below).
3. Register it in `Data/WorkoutPlans.swift`: one `static let`, one entry in `allPlans`.
4. Run the tests. `PlanLoaderTests` validates both bundled plans decode and that every exercise resolves; add pinned counts for your new plan in the same style.

The week view's plan switcher picks up anything in `allPlans` automatically.

## Core Design Decisions

### 1. Flatten the workout into a linear set sequence

A workout is a tree (Workout → Blocks → Exercises × Sets), but a runner needs a *list*. Everything expands to `[PrescribedSet]` in execution order — including superset interleaving (A1, A2, A1, A2 …) and circuit unrolling (Round 1 ex1-ex2-ex3, Round 2 …). The UI just walks `currentSetIndex` 0 → N.

### 2. Two set types, one interface

A set is either **rep-based** (user taps "Done" when finished) or **time-based** (auto-completes when countdown hits zero). Same `PrescribedSet` model — it has both `reps: Int?` and `durationSeconds: Int?`; whichever is non-nil drives behavior. HIIT intervals just become time-based sets.

### 3. State machine, not a pile of booleans

```
.notStarted  →  .performing(setIndex)  →  .resting(setIndex, secs)  →  .performing(setIndex+1) … →  .completed
```

Reset/skip transitions are explicit. No "if isResting && !isPaused && hasStarted" tangles. Each phase renders its own SwiftUI component under `Views/ActiveWorkout/`.

### 4. Reset granularity

Two resets, both wired:
- **Reset current set** — clears the timer, restarts the current set (mistake recovery).
- **Reset workout** — back to set 0. Confirmation prompt (destructive).

### 5. Media: progressive fallback

```
Exercise.videoURL             →  set?                    AVPlayer (looped, muted)
        ↓ no
Bundle: ExerciseMedia/{id}.gif                           AnimatedGIFView (ExerciseDB)
        ↓ no
Bundle: ExerciseMedia/{id}-0.jpg
       + ExerciseMedia/{id}-1.jpg                        TwoFrameAnimator (free-exercise-db)
        ↓ no
Exercise.staticImageName      →  set?                    Static image
        ↓ no
Exercise.formCues             →  always present          Icon + bullets
```

The `ExerciseMediaView` makes this transparent to its parent.

### 6. Plan identity and session logs

Plans are decoded **once** into `static let`s (`WorkoutPlans.swift`), so the generated `PrescribedSet` UUIDs stay stable for the app run — `WorkoutSessionManager` keys its in-session logged weights/reps by those ids. If persistence is added later, sets need stable string ids instead of per-run UUIDs.

### 7. Keep screen awake

```swift
UIApplication.shared.isIdleTimerDisabled = true
```

Wrapped in a SwiftUI `ViewModifier` so it auto-toggles on view appear/disappear. Critical: re-enable on disappear or you'll drain the user's battery.

## Exercise Media — Offline Bundling

Two sources, in priority order. The fetcher tries each; whatever it gets per exercise is what the app uses.

| Source | License | Format | Coverage |
|---|---|---|---|
| **[ExerciseDB v1](https://docs.ascendapi.com/products/edb-v1/overview)** (free hosted, no auth) | AGPL-3.0 | 180p animated GIF | Most exercises |
| [yuhonas/free-exercise-db](https://github.com/yuhonas/free-exercise-db) | Public Domain (Unlicense) | Two static JPEGs (start + end) | Fallback for anything EDB misses |

### Workflow

1. **Fetch all media** — run from the project root (the folder containing `varsha.xcodeproj`), since the script writes to `Varsha/Resources/ExerciseMedia` relative to the working directory:
   ```bash
   python3 varsha/fetch_exercise_media.py
   ```
   The script paginates ExerciseDB's free API, matches each exercise id via the `EDB_NAME_CANDIDATES` map, downloads the GIF if found, and falls back to free-exercise-db start/end photos via `FREEDB_FALLBACK_MAP`. New exercises need an entry in those maps. Missing media is fine — the app degrades to icon + form cues.

   **Flags:** `--gifs-only` skips the fallback (AGPL-only build), `--frames-only` skips ExerciseDB entirely (public-domain-only build, see License below).

2. **Xcode picks the files up automatically.** The project uses Xcode 16 synchronized folders — anything under `varsha/` (media, plan JSON, Swift files) is bundled without touching the project file. The lookup code (`ExerciseFrameLocator`, `PlanLoader`) tries the subdirectory first, then the bundle root, so it works whether or not the folder structure survives into the bundle.

### Per-exercise overrides

To upgrade a specific exercise to higher fidelity, set the appropriate field on its entry in `Resources/Plans/exercises.json` — no code changes:

| Field | Effect |
|---|---|
| `"videoURL": "..."` | Self-recorded video wins over GIF (`bundle://file.mp4` or a CDN URL) |
| Bundled `{id}.gif` exists | Animated GIF (default for matched exercises) |
| Bundled `{id}-0.jpg` + `{id}-1.jpg` exist | Two-frame animator (fallback) |
| `"staticImageName": "..."` | Single static image from the asset catalog |
| None of the above | Icon + form cues |

The 6–8 most heavily-loaded compounds (squat, RDL, bench, row, OHP, hip thrust, Bulgarian split squat, pull-up) deserve hand-recorded 5-second side-angle loops eventually.

## Building & Testing

```bash
# Build
xcodebuild -project varsha.xcodeproj -scheme varsha \
  -destination 'generic/platform=iOS Simulator' build

# Run the plan-loader tests (create a simulator first if none exist)
xcrun simctl create "varsha-test" \
  com.apple.CoreSimulator.SimDeviceType.iPhone-17 \
  com.apple.CoreSimulator.SimRuntime.iOS-26-4
xcodebuild -project varsha.xcodeproj -scheme varsha \
  -destination 'platform=iOS Simulator,name=varsha-test' \
  -only-testing:varshaTests test
```

`PlanLoaderTests` pins the exact expansion output of both bundled plans (set counts, interleaving order, rest conventions, labels, notes), so any JSON edit that changes shape fails loudly before it ships.

## Critical iOS Specifics

### Timer correctness
`Timer.scheduledTimer` runs on the main runloop and pauses during scrolling on the default mode. Use `.common` runloop mode, or use a `DispatchSourceTimer`, or use `Task.sleep` in async context. The session manager uses `Timer` with `RunLoop.main.add(timer, forMode: .common)` — see code.

### Background behavior
By default, when the app backgrounds, the timer stops. Two options:
1. **Accept it.** Keep the screen on (screen-wake modifier), problem solved.
2. **Continue in background** — requires `audio` background mode + a silent looping audio track. More complex, do later.

### Haptic + audio cues
Last 3 seconds of rest: tick haptic each second. Set complete: success haptic. Rest end: notification haptic. All free, no permissions.

## Future Enhancements

- **SwiftData persistence** — workout history; needs stable set ids (see design decision 6).
- **Apple Watch app** — heart rate tracking + on-wrist set completion. iOS app stays the "screen" while the Watch is the controller.
- **HealthKit** — write `HKWorkout` objects so workouts show in Apple Health.
- **Cycle awareness** — for the PCOS plan, optionally log cycle phase and auto-suggest yoga swap on heavy/PMS days.
- **Progressive overload tracker** — for each exercise, suggest next weight based on last session's reps and RPE.
- **Remote plans** — `PlanLoader` already decodes from `Data`; serving the plan JSON from a server enables over-the-air program updates.
- **Media list from data** — derive `fetch_exercise_media.py`'s exercise list from `exercises.json` instead of its hardcoded maps.
- **CloudKit sync** — sync workout data across devices, free with iCloud.
